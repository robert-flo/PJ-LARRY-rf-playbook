## 🗺️ El original en este stack

| Decisión (§) | Original | Aquí |
|---|---|---|
| 29.2 Disparador por horario | `/schedule` con cron (mínimo 1 h) | Local: timer de systemd (`OnCalendar=`). Nube: GitHub Action con `on: schedule` que lance un cloud agent |
| 29.2 Disparador por evento | PR o release de GitHub, etiqueta, `POST` a la URL de la rutina | GitHub Action con `on: pull_request`, `release`, `issues` o `workflow_dispatch` que llame al SDK. El texto que llega es dato no confiable, igual que en el original |
| 29.3 Contexto: repos | Varios repos por rutina | `cloud.repos` en `Agent.create` acepta una lista (el SDK de `sura-cloud`) |
| 29.3 Contexto: conectores | Drive, Slack, MCP de GitHub | Sin conectores (Cap. 26); `gh` dentro del agente |
| 29.4 Revisión agente sobre agente | Una segunda rutina revisa el PR | Un segundo cloud agent, o `/code-review` con el brief de `code-reviewer.md` (Cap. 22) |
| 29.4 Vigilancia humana | Abrir la sesión en la web | `cursor.com/agents/<bc-id>` o `sura-cloud send` |
| 29.4 Verificar la salida | Renderizar la página cambiada | La regla del Cap. 23: nombrar la comprobación mecánica antes de lanzar |
| 29.4 Antes de dejarla sola | Radio de daño, primera vez vigilada, puerta que se detiene y avisa | Igual; para avisar en local, `notify-send` como ya hace `sura-canaries` |

## ⚠️ Trampas encontradas

> [!WARNING]
> **1. El contexto es el techo.** Una rutina en la nube solo ve los repos que se le pasan en `cloud.repos`. Si falta uno, hace mal el trabajo sin avisar. Al diseñar la primera, listar todos los repos que necesita antes de lanzarla.
